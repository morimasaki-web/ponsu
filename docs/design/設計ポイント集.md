# 設計ポイント集（タスク完了ごとの学び）

目的: PonSu 開発を進めながら「なぜその設計にしたか」を言語化し、プロダクト設計スキルを積み上げる。

運用ルール:
- タスク（`docs/tasks.yaml` の `MVP-xxx`）が **done になったタイミング**で、ここに追記する。
- 1タスクにつき 5〜15 行程度でOK（短く、判断材料を残す）。
- “実装メモ” ではなく “設計判断メモ” を優先する（トレードオフを必ず1つ書く）。

---

## MVP-032 Usecase: create/submit/approve/reject（2026-01-12）

- 背景: request の主要フローを「イベント追記→同期投影」まで1操作/1TXで完結させたい。
- 決定: Usecase層でTX境界を持ち、`eventstore.Append` → `projector.RunOnceTx/CatchUpTx` を同一TX内で実行。
- 理由: at-least-once 投影を許容しつつ、read model と audit の整合を保つ（コミットで一貫性を確定）。
- トレードオフ: 同期投影でTXが長くなりやすい（将来はアウトボックス/非同期へ移行余地）。
- 学び: DBのユニーク制約（特に partial index と `ON CONFLICT`）の整合は、設計段階で「クエリ構文まで」セットで決める必要がある。

## MVP-040 WorkflowTemplate のRead Model（2026-01-13）

- 背景: 「申請」を作る前提として、承認ステップの雛形（テンプレ）を最小仕様で永続化したい。
- 決定: `workflow_templates` を Read Model として追加し、`definition` は JSONB で保持（スキーマ厳密化は後続タスクへ）。
- 理由: UI/GraphQL を先に進めるために、構造の柔軟性と実装速度を優先する（変更頻度が高い領域）。
- トレードオフ: JSONB は型安全/制約が弱いので、将来的に validation（JSON Schema等）や正規化が必要になる。
- 学び: 開発者ツール（sqlc/migrate）の実行経路は「Docker前提」だけにせず、host実行の代替手段を用意すると詰まりにくい。

## MVP-051 GraphQL リゾルバ（MVP最小Query/Mutation）（2026-01-15）

- 背景: SSR実装済みの主要フローを、SPA化/外部連携に向けてGraphQL経由でも実行できるようにしたい。
- 決定: Queryは read model（sqlc）を参照し、Mutationは既存Usecase（イベント追記→同期投影）を呼び出して結果をread modelから返す。
- 理由: 既存のTX/投影設計を再利用して一貫性を保ちつつ、API層は薄くして拡張点（認可/入力検証）を集中させる。
- トレードオフ: GraphQLの型（JSON/Time）は柔軟性を優先し、厳密なスキーマ検証は後続タスク（バリデーション/型付け）へ先送り。
- 学び: カスタムScalarは実装負債になりやすいので、まずは gqlgen の標準挙動（`map[string]any` / `time.Time`）に寄せると進捗が落ちにくい。

## MVP-070 添付（Storage抽象 + ローカル実装）（2026-01-17）

- 背景: 添付は後続でMinIO（S3互換）へ移行したいが、まずは開発効率重視でローカル保存で成立させたい。
- 決定: `internal/usecase/attachments.Storage` を定義し、`internal/infrastructure/storage.LocalStorage` をまず実装。メタ情報は read model（`request_attachments`）へ保存。
- 理由: ストレージ切替（MVP-071）に備えて境界を先に作りつつ、APIはHTTPの multipart で最短に疎通できるようにする。
- トレードオフ: GraphQLのファイルアップロードは扱いが重いので今回はHTTP APIに寄せ、画面/GraphQLへの統合は後続タスクへ。
- 学び: ローカルFS保存でもパストラバーサル対策（keyの正規化・baseDir逸脱防止）とサイズ上限（`MaxBytesReader`）は最初から入れておくと安全。

## MVP-071 添付（MinIO: S3互換実装 + デモ向け設定）（2026-01-17）

- 背景: デモ運用で「S3互換ストレージに保存される」を満たし、将来のクラウドS3移行も見据えたい。
- 決定: AWS SDK v2 のS3クライアントでMinIOへPut/Get/Deleteし、`PONSU_ATTACHMENTS_STORAGE=local|minio` で切替できるようにした。
- 理由: Storage抽象（MVP-070）を崩さずに実装を差し替え、環境変数だけでデモ構成へ寄せられる。
- トレードオフ: 署名URLはUI/期限/権限の扱いが増えるため今回は見送り、既存のdownloadエンドポイント（プロキシ配信）で閲覧要件を満たす。
- 学び: MinIOは path-style が前提になりやすいので、SDK設定（endpoint + `UsePathStyle`）を最初から構成可能にしておくと詰まりにくい。

## MVP-080 Slack通知（Incoming Webhook）（2026-01-18）

- 背景: MVPで「外部に通知が飛ぶ」体験を最短で作り、デモの説得力を上げたい。
- 決定: Slack Incoming Webhook に `text` をPOSTする最小実装にし、提出/承認/却下のタイミングで通知する（SSR/GraphQLどちらの経路でも同じusecaseが動く）。
- 理由: Bot/OAuthは重いので避け、環境変数（`PONSU_SLACK_WEBHOOK_URL`）だけで有効化できるようにする。
- トレードオフ: 通知失敗で業務操作が止まるのは避けたいので、通知は best-effort（失敗しても主処理は成功）とした。
- 学び: SlackにURLを載せるには「外部に見えるベースURL」を別途持つ必要があるので、`PONSU_PUBLIC_BASE_URL` を追加してリンク生成を安定させた。
